## Long-term Knowledge

### Architecture

<!-- lore:01a09ffd-85ac-782c-bd24-e8c98ec7932b -->
* **SceneFit modular monolith**: SceneFit is a single modular Next.js application, not a split frontend/backend stack. Chose one app with clear feature boundaries over a separate API because the MVP is a one-room, ten-product browser visualizer and the extra service layer would add complexity without product value.

<!-- lore:01a09ffd-85b4-7f83-a1e6-4a054b5c6e27 -->
* **Zod scene schema authority**: The Zod scene schema is the runtime authority for persisted scene data. Chose schema-driven validation over trusting UI state or duplicated type definitions because saved scenes must be validated server-side, versioned, and kept separate from transient UI state.

### Pattern

<!-- lore:01a09ffd-85cf-7290-b87c-8ee17af9a766 -->
* **PR template issue #1**: For issue #1, `.github/pull_request_template.md` is the required PR template and must include Summary, Related issue, Changes made, Verification performed, Screenshots or recordings for UI changes, Risks or limitations, plus a checklist for scope, tests, lint/typecheck/tests/build, secrets, and docs. Chose a narrow template-only change over broader repo setup because the issue explicitly excluded app initialization, `spec.md`/`AGENTS.md` edits, dependency changes, and CI configuration.

<!-- lore:01a09ffd-85c7-7788-b8d8-2f20c598d9a6 -->
* **repo-setup worktree flow**: Use `repo-setup` to refresh the repo and create an isolated worktree before editing. The main clone should stay untouched, because the workflow explicitly avoids destructive cleanup there and the worktree is the safe place for branch-specific changes.

<!-- lore:01a09ffd-85bd-76bb-8568-aa81eefd6770 -->
* **Webhook self-loop guard**: If `payload.sender.login` matches Jared/the configured bot identity, return `SKIPPED: self-triggered`. This looks like a missed automation opportunity, but it prevents the agent from re-triggering on its own comments or PR activity; only a relevant CI `check_suite.completed` event is exempt.

### Preference

<!-- lore:01a09ffd-8568-7b31-ab85-ddec96a92200 -->
* **force-push someone else's branch**: Never force-push to someone else's branch. It seems harmless when you only need to update a PR, but it can rewrite another person's published history; only `--force-with-lease` on your own branch is acceptable after a rebase.

<!-- lore:01a09ffd-8557-70c5-aa67-eca46c3bd62f -->
* **git reset --hard and git clean -fd**: Never use `git reset --hard` or `git clean -fd` in the main clone. They look like a fast way to recover a dirty workspace, but they can destroy uncommitted work or local state in the shared repo; use an isolated worktree instead.

<!-- lore:01a09ffd-8590-7747-a005-51a7221ce2e1 -->
* **Human maintainer approval**: Always keep a human maintainer in the approval/merge loop. Automated agents can prepare changes and draft PRs, but final approval and merge authority stay with a human.

<!-- lore:01a09ffd-8588-7a07-9edb-3294ee6a056d -->
* **Jared-triggered work**: Never create work merely in response to Jared's own comments or PR activity. Those events look like normal workflow triggers, but this repo's self-loop guard treats them as non-actionable unless the event is a relevant CI `check_suite.completed`.

<!-- lore:01a09ffd-85a3-7931-a6a1-54b60a3fab54 -->
* **Never log secrets**: Never log secrets, full authorization headers, webhook secrets, or raw credentials. Logging them seems useful for debugging, but it leaks sensitive values into PRs, screenshots, fixtures, and test output; keep secret-bearing data out of all surfaced artifacts.

<!-- lore:01a09ffd-8599-7973-a07f-46bb21c7b339 -->
* **Never mutate original project**: Never mutate the original project directly. It is easy to think the main clone is the canonical place to work, but this workflow uses an isolated worktree so the source checkout stays untouched.

<!-- lore:01a09ffd-8574-722c-80ee-90a2b1517785 -->
* **PR ready claim**: Never claim a PR is ready unless the required validation has actually been run. It is tempting to treat a draft or partial check as sufficient, but this repo requires explicit evidence before a ready-for-review status.

<!-- lore:01a09ffd-857f-706d-aae2-ecbf09aae027 -->
* **Supabase service-role client exposure**: Never expose Supabase service-role credentials to client code. It may seem convenient for direct browser access, but the service role bypasses security boundaries; keep it server-only and validate environment access centrally.
